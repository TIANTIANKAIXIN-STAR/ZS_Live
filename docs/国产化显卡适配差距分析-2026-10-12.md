# ZS_Live × 国产化显卡适配差距分析报告

> 日期：2026-10-12 · 范围：从「当前平台」到「能在国产 GPU 上成熟稳定商用推流」的完整差距清单
> 数据依据：本仓库代码实地核查 + 国产 GPU 厂商公开资料（摩尔线程官网/开发者中心、信创云渲染实测案例）

---

## 〇、一句话结论

**平台 80% 的代码是 GPU 厂商无关的（Node 调度、MediaMTX、WebRTC 播放、RTMP 推流器），真正卡脖子的只有三个点：①UE 插件的编码器只有 NVENC/AMF 一条路；②GPU 探测/绑卡只认 nvidia-smi；③没有硬编码失败后的软编码兜底。**
国产卡里**摩尔线程**（MTT S 系列）具备「UE5 渲染 + 硬件编码 + FFmpeg/VAAPI 开放接口」的完整能力，是第一适配目标；**砺算科技**（LX 7G100 系列，2026 年 5 月发售）渲染侧更强（WHQL 认证 + DX12/Vulkan1.3 + UE/数字孪生官方适配 + SR-IOV 16 路 vGPU），但 Linux 编码接口开放性待确认，列为第二适配目标——**建议双供应商策略**；景嘉微/风华只能降级跑，不适合做实时推流主力。

## 一、现状盘点：代码里的三处「NVIDIA 硬绑定」（已实地核查）

| # | 位置 | 现状 | 换国产卡后的后果 |
|---|------|------|------------------|
| 1 | `ue-plugin/.../SFVideoPipeline.cpp:97-131` | 编码器枚举走 UE AVEncoder 工厂，依赖官方 `HardwareEncoders` 插件（EncoderNVENC/EncoderAMF），**只挑 H264，找不到就失败** | 国产卡没有 AVEncoder 实现 → 直接报 `No encoders registered`，推流起不来。**这是最硬的一堵墙** |
| 2 | `server/src/gpuAllocator.js:163-213` + `gpuMonitor.js` | GPU 探测只有 `nvidia-smi` 一条链路；绑卡靠 `-graphicsadapter=N` + `CUDA_VISIBLE_DEVICES` | 国产卡监控页全空、无法按卡调度；`CUDA_VISIBLE_DEVICES` 对 MUSA 无意义 |
| 3 | `SFVideoPipeline.cpp` 采集→编码链路 | backbuffer 捕获（RDG）是 RHI 层、厂商无关 ✅；但编码输入帧要求与硬编码器零拷贝对接 | 即便有第三方编码 SDK，也**没有管道把 UE 帧送出去**（缺 readback→CPU→外部编码 的路径） |

**厂商无关、不用动的部分（好消息）：**
- 调度服务/管理后台/会话编排（Node.js）✅
- MediaMTX（纯 Go，官方有 linux amd64/arm64 构建，无 GPU 依赖）✅
- WebRTC/WHEP 播放链路、浏览器解码 ✅
- 自研 RTMP 推流器（纯 socket 实现）✅
- 音频管线（AAC/PCMA 软编码）✅
- 实例池/排队/绑卡调度框架（逻辑通用，只是探测源要换）✅

## 三、差距清单（按优先级，P0 = 不做就上不了国产卡）

### P0-1 编码链路厂商化 ⭐ 核心中的核心
- **缺**：编码器抽象层。现在 `SFVideoPipeline` 直接调 AVEncoder 工厂，没有「编码后端」接口。
- **要建**：`ISFEncoderBackend` 接口（Initialize/EncodeFrame/Packet 回调），下挂三个实现：
  1. `AVEncoderBackend`（现有 NVENC/AMF，保持不动）
  2. `FFmpegPipeBackend`（readback→CPU→管道喂外部 ffmpeg 进程，ffmpeg 用 `-hwaccel vaapi` / 摩尔线程定制版调硬编码）——**最快落地的国产化路径**
  3. `DXVABackend`（Windows 下摩尔线程 DXVA 2.0，中期）
- **工程量**：FFmpeg 管道方案 2~3 周（含 readback 调优）；零拷贝 SDK 方案（DirectStream）再加 2 周。

### P0-2 软编码兜底（x264/openh264）
- **缺**：硬编码失败 = 整路推流失败（9-29 的 15 连跪就是这么死的）。
- **要建**：AVEncoder 不可用时自动降级 CPU 软编码（720p30 可行，1080p60 吃紧需降帧）。
- **注意**：平行云的经验——硬↔软切换**必须在关键帧边界**做，否则花屏；我们已有 `RequestKeyFrame()`，切换前先强制关键帧即可。

### P0-3 GPU 探测/绑卡多厂商化
- **缺**：`gpuAllocator.js` 只认 nvidia-smi。
- **要建**：探测器抽象 `queryGpus()` → 按可用工具链依次尝试：`nvidia-smi` → `mthreads-gmi`（摩尔线程监控接口）→ `rocm-smi` → 纯 Vulkan 枚举兜底（`vulkaninfo --summary` 或直接读驱动 API）。输出统一成现有 `{index,name,vramTotalMB,...}` 结构，后台/配额/绑卡逻辑**零改动**。
- 绑卡参数：摩尔线程用 `MUSA_VISIBLE_DEVICES`（MUSA 兼容 CUDA 语义）+ `-graphicsadapter`；vGPU 场景改认 VF 设备。
- **工程量**：3~5 天。

### P1-1 信创 OS 部署包
- **缺**：麒麟 V10 / 统信 UOS 的验证。风险点：better-sqlite3 需本机编译（要 gcc/make 离线包）、内核版本与 GPU 驱动强绑定（厂商 deb 包指定内核）、systemd 单元缺失、Xvfb 无头渲染在国产 OS 上的显示服务差异。
- **要建**：离线整包（node 运行时 + node_modules + mediamtx + 驱动校验脚本 + systemd 模板），安装脚本先跑「环境体检」再部署。

### P1-2 编码格式策略升级（AV1/H.265）
- 国产卡全系支持 **AV1 硬编码**，同画质省 30%+ 码率，WebRTC 原生支持。当前管线写死 H264。
- **要建**：编码格式做成模板级配置（h264/h265/av1），推流侧 MediaMTX 和播放器 SDP 都已具备条件；默认仍 H264（兼容性最好），内网/自研播放器场景可开 AV1。

### P1-3 多实例并发密度验证
- NVENC 有会话数限制（消费卡 3~5 路），摩尔线程按编码核算（S80=2 核、S4000=4 核，官方标 48 路 1080p30 是极限转码场景，**实时低延迟编码的实际并发必须实测**）。
- **要建**：并发压测脚本（已有 e2e_test.js 基础），产出「每卡稳妥并发数」写入配额默认值。

### P2-1 ARM 服务器支持
- 飞腾/鲲鹏 + 摩尔线程的组合：UE 官方 Linux ARM64 桌面渲染支持仍在实验阶段，**当前不可承诺**；海光/兆芯（x86）+ MTT 才是可落地组合。文档里要写明这个边界，避免投标时被问倒。

### P2-2 vGPU/虚拟化调度
- 摩尔线程 SR-IOV 把一卡切成多 vGPU 后，实例隔离模型从「进程绑卡」变「进程绑 VF」，调度器要识别 vGPU 拓扑（MTGPUManagementCenter 可查）。政企私有云场景会用到，普通单机场景用不到。

### P2-3 跨厂商自动化测试
- 建「兼容性矩阵」：{NVIDIA, AMD, MTT} × {Win, Linux} × {720p/1080p/4K} 的冒烟测试，接入每日自动化（平台已有完整 API，写脚本即可）。

## 五、采购与验证 Checklist（买卡前必做）

1. **首选验证卡**：MTT S80（桌面卡，便宜，2 编码核）→ 验证通过后上 S4000（数据中心，4 编码核 + SR-IOV）。**并行申请砺算 LX Pro/Ultra 测试卡**（专业线 24GB + SR-IOV，面向云渲染/数字孪生场景，厂商有 B 端送测通道）。
2. **向厂商索取**：
   - 摩尔线程：Linux 定制 ffmpeg + libva 包、MT DirectStream SDK 试用、MTGPUManagementCenter 开发库、UE 适配白皮书（与蕊霖 Real-Link 有 UE5 官方适配合作）。
   - **砺算（三个必问，答不上来就降级为渲染专用卡）**：①Linux 下是否暴露 VAAPI/FFmpeg/DXVA 编码接口？②**H.264 硬编码是否支持**（公开规格只写了 HEVC/AV1 编码，H.264 对我们 WebRTC 兼容性是刚需）？③单卡实时编码并发路数与 SDK（云渲染/串流方向）是否开放？
3. **到货首日验证三件事**：`vainfo`（VAAPI 编码器列表）→ ffmpeg 命令行编码一个测试文件 → UE5 Demo 工程跑 30 分钟看驱动稳定性。
4. **配套服务器**：海光/兆芯 x86 + 麒麟 V10 SP3（或统信 UOS 服务器版），**不要**选 ARM 平台（UE 渲染跑不了）。注：砺算官方宣称兼容飞腾/龙芯平台，但那是图形桌面场景，UE 渲染推流仍坚持 x86。
5. **驱动-内核绑定**：国产卡驱动包绑定内核版本，升级 OS 内核前必须确认驱动兼容矩阵——这条写进运维手册。砺算驱动迭代极快（游戏帧率随驱动版本肉眼可见提升），部署包务必锁定「驱动版本 + 内核 + ffmpeg」三件套组合并留回滚包。
6. **双供应商价值**：政企信创招标通常认可「多源适配」；MTT 与砺算任一断供/涨价时平台可平滑切换，阶段①的编码后端抽象就是为此设计的。

## 六、风险与边界（要对外说清楚的）

- **景嘉微/风华卡不接实时推流**：只能 ES3_1 降级渲染，画质和稳定性都不达标，如客户指定需签「功能降级确认」。
- **砺算的三处未知必须先问清**：H.264 硬编码有无、Linux 编码接口开放度、实时编码并发路数——三项都达标才能进编码主力池，否则只作渲染/演示节点。另外砺算消费卡驱动很新（2026 年 7 月零售），生产环境只用其专业线（LX Pro/Ultra）并锁驱动版本。
- **ARM + UE 渲染不可承诺**：UE 官方 Linux ARM64 桌面渲染仍是实验状态。
- **国产卡驱动迭代快**：ffmpeg 定制版、libva 扩展随驱动版本变，部署包要锁版本组合并留回滚包。
- **编码并发数没有官方承诺值**：一切以实测为准，配额默认保守（S80 建议先按 2 路）。

## 七、阶段①实施完成记录（2026-10-12，已上线并通过 e2e）

目标卡已定为**砺算 LX 系列**。在卡未到货前，所有「不依赖卡」的准备已完成：

### 已完成（服务端）
- **gpuProbe.js（新）**：多厂商 GPU 探测链 nvidia-smi → 自定义厂商命令 → vulkaninfo 兜底；探测顺序可在系统设置 `gpuProbeOrder` 配置（砺算卡到货后填其 CLI 即可接入）
- **绑卡环境变量多厂商化**：`gpuBindEnvVars` 设置项可改（默认 CUDA_VISIBLE_DEVICES,NVIDIA_VISIBLE_DEVICES），按厂商适配
- **模板新增两列**：`encoder_backend`（ave/ffmpeg/auto，默认 ave=行为不变）+ `codec`（h264/hevc 预留）
- **系统设置新增「编码与国产化适配」卡片**：ffmpegPath、gpuProbeOrder、gpuBindEnvVars

### 已完成（UE 插件 StreamForge）
- **编码后端抽象** + 新命令行 `-SFEncoder=ave|ffmpeg|auto`、`-SFCodec`、`-SFFFmpegPath`
- **SFFmpegEncoder（新）**：GPU readback → ffmpeg stdin 裸流 → libx264 软编码 → Annex-B 分包 → 复用现有 RTMP 推送。改编码参数即接砺算 VAAPI/DXVA
- **auto 模式**：优先 NVENC/AMF 硬编码，失败自动降级 FFmpeg 软编码（9-29 那种「15 连跪全灭」不会再发生）
- ave 默认路径**一行未动**，NVIDIA 现状完全保留

### e2e 验证结果（本机 4090）
| 模板 | 后端 | 结果 |
|------|------|------|
| 模板3 720p30 | ffmpeg（libx264 软编码） | ✅ 10s 推流成功，码率正常 |
| 模板2 4K30 | auto → NVENC 硬编码 | ✅ 15s 推流成功，4K 码率正常 |

### 砺算卡到货后只剩三件事（阶段②）
1. 向砺算确认：H.264 硬编码有无、Linux VAAPI/Windows DXVA 接口、编码并发路数
2. SFFmpegEncoder 增加砺算编码参数分支（h264_vaapi / 厂商 SDK），约 1~2 周
3. 系统设置 `gpuProbeOrder` 填入砺算管理 CLI，监控/调度即接入

### 注意事项
- 新插件已编译并部署到 **UEtest 包**（Package/Windows/UEtest/Binaries/Win64/UEtest.exe）
- **J002 模板（E:\UPROJECT\J002）仍是旧插件**：要用软编码兜底/砺算后端，需对 J002 工程重新打包
- 软编码性能边界：libx264 720p30 轻松；1080p60 单实例约占 4~6 核；4K 软编码不现实（4K 场景必须硬编码，这正是砺算卡的价值）
