# 推流连接失败故障复盘（2026-10-12）

## 故障现象
13:30 前后三个模板全部「推流连接失败」：观看页无画面，4K 模板陷入 RTMP 重连死循环。

## 根因（三层叠加）

### 1. NVENC 持续枚举失败（诱因）
J002（auto 模式）启动时 `No encoders registered`，NVENC 注册不上 → 自动降级 FFmpeg 软编码。13:30 起从间歇变为持续（重试 3 次均失败）。**4090 的 NVENC 健康需要关注（驱动/占用），但与本次平台代码无关。**

### 2. MediaMTX 轨道锁定竞态（致命 bug 一）
MediaMTX 在 publish 后按「先到的媒体包」锁定 path 轨道：
- FFmpeg 后端首帧慢（readback + x264 启动 1~3s），音频 G711 包（20ms 一包）先到
- path 被锁成「纯音频轨」→ 视频包到达时被 `video track is not set up` 踢断
- 插件重连 → sequence header 重发 → 又触发问题 3 → 死循环

旧 NVENC 路径不触发是因为编码器就绪快，视频 seq header 总是先于音频到达。

### 3. x264 slice 数超 MediaMTX NALU 上限（致命 bug 二）
- `-tune zerolatency` 隐含 `sliced-threads`，x264 按逻辑核数切 slice
- 14700K 28 线程 → **每帧 28 个 slice NALU**，MediaMTX AVCC 解码上限 25 → 每帧都被踢断
- 实测实锤：AU#0 = 31 NALU（SPS+PPS+SEI+28 slice），P 帧 28 NALU
- 720p 不超（x264 低分辨率自动减线程），所以软编码 e2e 之前能通过

### 附带：播放器 WHEP 无重试
ready 消息早于 RTMP publish 1~3 秒，WHEP 404 `no stream is available` 后直接死屏不重试。

## 修复内容（已上线）

| 修复 | 位置 | 机制 |
|------|------|------|
| x264 `threads=8` | SFFmpegEncoder.cpp | 每帧 8 slice + 头 ≈ 11 NALU < 25 上限（实测验证） |
| 首包延迟启动 | SFVideoPipeline + StreamForgeModule | 视频采集先开，游戏线程 Ticker 等首个 AU 入队后再启动 RTMP/音频（5s 兜底）；不能在游戏线程阻塞等（Slate present 由游戏线程驱动，阻塞必死锁超时） |
| auto 降级前重试 AVE ×3 | SFVideoPipeline.cpp | NVENC 枚举偶发失败不再直接掉软编码 |
| 播放器 WHEP 自动重试 | player.js | 404/网络错误重试 12 次 × 1.5s，覆盖实例启动窗口 |

## 经验沉淀
1. **MediaMTX 的 track 锁定**：publish 后首包定轨，中途不能新增轨。推流端必须保证视频 seq header 先达。
2. **x264 zerolatency = sliced-threads**：多核机器 slice 数 = 线程数，与 MediaMTX 25 NALU 上限冲突时必须显式 `threads=N`。
3. **UE 游戏线程不能阻塞等渲染回调**：Slate present 由游戏线程驱动，阻塞即死锁；异步等待用 FTSTicker（注意委托名是 FTickerDelegate，类名是 FTSTicker）。
4. NVENC 故障期间平台靠软编码兜底维持服务——这正是 auto 模式的设计目标，本次实战验证成立。
