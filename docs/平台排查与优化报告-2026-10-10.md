## 一、画质预设改动后推流连接不上（已定位 + 已加固）

### 结论先行

**当前代码（服务 2026-10-10 16:50 重启后）下，全部画质预设均可正常推流。**
在线实测结果（J002 / UE5.7 / RTX 4090，逐项验证）：

| 预设 | 编码器 | RTMP 发布 | MediaMTX 流 |
|---|---|---|---|
| 720p30 / 4Mbps | ✅ | ✅ | ✅ |
| 1080p60 / 16Mbps | ✅ | ✅ | ✅ |
| 4K30 / 28Mbps | ✅ (encodeMs≈7ms) | ✅ | ✅ H264+G711 |
| 4K60 / 35Mbps | ✅ (encodeMs≈8ms) | ✅ | ✅ |

### 历史 Bug 的两个真实根因（日志实锤）

1. **NVENC 编码器注册失败 → 插件放弃 → 实例变"僵尸"**（J002-backup-2026.09.29-02.26.43.log）
   - 现场：`No encoders registered. Enable the 'HardwareEncoders' plugin` 连续 15 次重试失败 → `giving up`。
   - 此时控制通道从未启动（原代码里 Control 在视频管线成功后才 Start）→ 服务端看不到任何错误，
     实例卡在 spawning 状态直到 120s 超时 → 用户侧表现为"推流一直连不上"。
   - 触发条件：GPU 瞬时状态（显存被本地大模型占用、驱动异常、多进程争抢 NVENC 会话）。
     同日 30 分钟后相同参数即恢复正常，说明是间歇性环境问题，不是参数问题。

2. **旧版服务端分辨率注入缺陷（09-29 05:41 已修）**
   - 当天 02:57~05:42 的 4K 运行日志中，命令行是 `-ResX=1280 -ResY=720` 配 `-SFWidth=3840`：
     渲染背缓冲 720p 拉伸到 4K 编码 → "改了预设画质不对/发糊"。
   - 磁盘上的 instancePool.js 已有修复（注入 `-ForceRes -ResX=w -ResY=h -ExecCmds=r.SetRes ...`），
     今天实测确认生效。

3. **附带陷阱：Node require 缓存。** 改了 server 代码不重启服务 = 跑的还是旧逻辑。
   今后改完服务端代码务必重启（启动器「一键启动」重跑即可）。

## 二、UE5.4 打包程序兼容性

**结论：插件按 5.4+ 设计，兼容性基本没问题，但建议做一次 5.4 实际打包验证。**

依据：
- `SFVideoPipeline.cpp` 里 `SF_AVENCODER_DEPRECATED` 宏对 `ENGINE >= 5.4` 统一关闭弃用告警
  （AVEncoder 在 5.4 起标记 deprecated，功能到 5.8+ 仍可用）；
- `StreamForge.uplugin` 未锁 `EngineVersion`，5.x 任意版本可加载；
- 依赖模块（AVEncoder / EncoderNVENC / EncoderAMF / WebSockets / Slate / AudioMixer）在 5.4 全部存在；
- 使用的 RHI API（`ERHIAccess`、`FRHITextureCreateDesc`、`TransitionAndCopyTexture`）均为 5.3~5.4 时代接口；
- 当前实测在 5.7（J002）跑通，5.7 能过基本排除 5.4 特有的 API 缺失问题（接口越新越少才对）。

风险点：5.4 的 `HardwareEncoders` 插件内部 NVENC 注册时序与 5.7 略有差异——
正好本次加固的"重试 + fail-fast + 错误上报"机制覆盖了这类时序问题。

**唯一可靠的验证方式**：用一个 5.4 工程挂插件打一次包（Build.bat 两步法照旧）。

### 启动器（ZSLiveLauncher，.NET9 WinForms）

1. **服务自愈**：定时探测 MediaMTX/调度服务进程，挂了自动拉起（现在只显示失败日志）。
2. **开机自启 + 托盘常驻**：服务器场景刚需，加个注册表自启动开关。

4. **GPU 面板**：拉 `/api/admin/gpus` 显示显存/利用率/温度（服务端数据已有）。
5. **一键"停止全部 UE 实例"**：打包前必做动作，现在要切到后台操作。
6. **实例错误直显**：配合本次 `stats.lastError`，实例行直接显示失败原因。

### 管理后台（web/admin，零构建 SPA）

1. **实例表加"错误"列**：`lastError` 有值显示红点 + tooltip（配合本次修复）。
2. **默认密码治理**：admin/admin123 首次登录强制改密（公网部署安全隐患）。
3. **实时推送**：实例状态改 WebSocket 推送替代 2s 轮询，多实例时更流畅。
4. **模板保存前置校验**：按分辨率/码率估算显存与带宽需求，超出时给黄色警告。

## 五、Linux 上能否稳定运行推流

**结论：架构上完全支持，可以稳定跑；但有四个具体的坑要处理。**

已具备：插件 Vulkan+NVENC 路径（`CreateEncoderInputForRHI` Vulkan 分支）、
PCMA 音频（WHEP 原生可播）、`start-linux.sh` 一键启动、跨平台打包文档（含 chmod 执行位修复）。

坑与对策：
1. **无显示器服务器渲染**：UE Linux 的 `-RenderOffScreen` 仍需可用的 EGL/GLX 环境，
   建议部署 Xvfb 或保留一张亮机卡输出；这是 Linux 上最大的坑。
2. **better-sqlite3 ABI**：必须目标机上 `npm install`（start-linux.sh 已自动处理）；
   换 Node 大版本要重装。
3. **NVENC on Linux**：需要 NVIDIA 驱动完整安装（含编码库）；Vulkan 渲染 + NVENC 编码双依赖。
4. **服务化**：建议补 systemd unit（开机自启 + 崩溃自动拉起），脚本已具备条件。

## 六、国产显卡能否稳定替换适配

**结论：渲染"有机会"，编码是硬门槛；短期有兜底方案，长期需适配工程。**

- **渲染面**：UE 走 Vulkan。摩尔线程（MTT S80/S4000）Vulkan 驱动日趋成熟，有机会跑起来，
  但 UE 大量用 NVIDIA 扩展（DLSS、部分光追/mesh shader 路径），需逐场景验证，性能打折。
  景嘉微/壁仞等在 UE 上的成熟度更低。
- **编码面（硬门槛）**：现在编码走 UE HardwareEncoders（**仅 NVENC/AMF**），
  国产卡都没有兼容编码器 → 直接换卡 = 无法推流。
- **信创整机注意**：飞腾/鲲鹏（ARM）跑不了 UE 渲染打包程序（UE 的 Linux ARM64 仅支持专用服务器）；
  国产化整机只能选 x86 CPU（海光/兆芯）+ 国产 GPU。

适配路径（建议组合）：
1. **软编码兜底（改动最小，立即可做）**：`SFVideoPipeline` 已单点封装编码创建，
   加 `-SFEncoder=software` 走 AVEncoder 软件 H264（x264）；14700K 的 28 线程跑 1080p30 可接受，4K 不行。
2. **FFmpeg 外挂编码（通用性最强，商用方案常见兜底）**：背缓冲纹理 → 拷贝到 CPU/共享内存 →
   ffmpeg 子进程编码（libx264 或国产卡自带 VPU SDK，如摩尔线程 MUSACore）→ RTMP。
3. **等官方 UE 适配包**：摩尔线程有 UE 适配驱动/编码 SDK 体系，需商务对接；
   海光 DCU 走 ROCm/oneAPI 路线。

## 七、Windows / Linux 部署便捷性

| | Windows | Linux |
|---|---|---|
| 目标机依赖 | 仅 GPU 驱动（安装包自带 Node 运行时） | Node 18+（自装）、NVIDIA 驱动 + Vulkan、bash |
| 一键化 | ✅ Inno Setup 安装包：自动 .env/防火墙/MediaMTX 初始化、播种模板 | ⚠️ start-linux.sh 一键，但依赖在线 npm install（离线环境会失败） |
| 服务化 | 启动器图形界面 | 无 systemd unit（裸 nohup） |
| UE 程序部署 | 手工拷贝 + 后台填路径 | 手工拷贝 + chmod + 填 .sh 路径 |

Linux 补齐建议：
1. 做离线整包（tar.gz 预置 node_modules + mediamtx 二进制），`install-linux.sh` 解压即用；
2. 附带 `zs-live.service` systemd 模板（开机自启 + Restart=always）；
3. 中期做"程序包管理"（后台上传 zip 自动部署注册，双平台通用）。
